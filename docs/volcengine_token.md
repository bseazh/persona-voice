# 火山引擎 Seeduplex：电话 Token 消耗、计费边界与逐响应时延

日期：2026-11-05。豆包端到端实时语音模型 `1.2.6.1`，音色 `zh_male_xiaotian_jupiter_bigtts`，路线 `doubao-realtime`。参照 [百度 Token 报告](baidu_token.md) 的结构整理；数据来自已有真实电话，不为编写报告再次拨号。

**当前完成一次完整两分钟测试，另有一次56.576秒的失败样本；不是两次完整两分钟验收。** 修复后电话持续123.267秒，6轮可测响应平均368.6ms；该时延仅为识别最终文字到Agent首音频。供应商返回total_tokens合计7246，输入输出分类合计5198，缓存字段存在口径差异，详见下文。

## 计费口径

官方计费依据：https://docs.volcengine.com/docs/doubao-voice/billing-instructions?lang=zh ，查阅日期2026-11-05，页面更新时间2026-09-29 18:56:11。采用“按调用后付费 → 豆包实时语音大模型”主价格表，不套用音频生成、语音合成或其他产品单价。

计数来源为真实 `response.done.response.usage`。本次以同一供应商连接内的唯一 `event_id` 去重。日志中的usage关联response_id为null，因此不能宣称已按response_id核验每条响应的用量覆盖，也不能将用量表与时延表机械地逐行合并。不同连接的event_id可能重复，后续跨连接统计须加入连接标识。

### 完整两分钟样本：费用与1.2倍换算

主估算假设：普通输入字段与cached字段分别计费。依据是本次total_tokens=普通输入+输出+cached，且官方费用示例将普通输入与cached分项相加。**这支持该估算，但文档未明确本版本usage字段的包含关系，仍需账单核验。**

|费用项|观测Token|单价：元/百万Token|标价费用：元|
|---|---:|---:|---:|
|输入文本|2483|10|0.024830|
|输入音频|730|80|0.058400|
|输入文本缓存|2048|5|0.010240|
|输入音频缓存|0|5|0.000000|
|输出文本|575|80|0.046000|
|输出音频|1410|300|0.423000|
|合计|7246（按分项独立口径）|—|**0.562470**|

计算公式：

```text
模型标价费用 = (2483×10 + 730×80 + 2048×5 + 575×80 + 1410×300) / 1000000
             = 0.562470 元
乘1.2后的预算 = 0.562470 × 1.2 = 0.674964 元
实际接通时长 = 123.2666244506836 秒 = 2.054443741 分钟
原价折合每分钟 = 0.562470 × 60 / 123.2666244506836 = 0.273782 元/分钟
预算折合每分钟 = 0.674964 × 60 / 123.2666244506836 = 0.328539 元/分钟
```

因此本次完整样本可按 **约0.33元/分钟（模型标价×1.2）** 做预算。以相同发言比例外推，标准120秒预算约0.657077元；这不是另一通真实两分钟的扣费。输出音频是主要费用来源；说话比例、上下文与缓存命中变化会改变每分钟价格，不能当作固定套餐价。

缓存备选口径：如果后续确认2483个输入文本Token已经包含2048个缓存Token，则普通输入文本应为435；同样单价下标价费用为0.541990元，乘1.2为0.650388元，折合0.316576元/分钟。**当前主预算采用较高的0.328539元/分钟，备选值不是已确认折扣。**

## 接入与限制

沿用原有LiveKit房间、AgentSession、RealtimeController、Asterisk/SIP与安卓SIM网关，新增的是豆包模型适配器，不是重新建立一套通信架构。豆包使用原生JSON WebSocket协议；业务控制复用，不代表其协议与Qwen相同。

输入16kHz单声道PCM16，每帧20ms；输出24kHz PCM16。开场在主会话中合成。已具备转录、取消和结束控制，但当前完整电话验收只证明定时挂断路径成功，不把它算作真人插话或自然告别挂断的完整验收。

## 时延口径与逐响应结果

时延起点：服务端收到 `conversation.item.input_audio_transcription.completed`；终点：Agent记录 `voice.realtime_first_audio`。按最近一个未配对的识别完成事件关联随后首音频，排除开场；这是事件关联，不是音频样本级trace。

Agent输出时刻取 `voice.turn_timing.metrics.started_speaking_at`，通过message_id与response_id匹配。它也不是手机听筒的可听时刻。当前没有可核验的SDK模型TTFT或用户真实停口到手机播放的完整时延，均记N/A。

## 输入队列积压：原因与修复效果

旧逻辑发送完成后再等待20ms，导致发送耗时和调度误差逐包累积，输入速率长期高于输出。修复后按绝对音频时间轴每帧推进20ms，长停顿后的追赶限制40ms，保留100帧有界队列保护；没有扩大队列或静默丢弃音频。

本地相同回归：持续输入150帧、每次发送模拟8ms开销。旧逻辑3秒积压52帧，断言失败；新逻辑队列少于10帧并发送完成，10项适配器测试通过。

完整电话记录24个五秒周期：队列采样10～13帧，区间峰值13帧，未持续增长；约对应200～260ms音频排队量。最大单次发送耗时2.120ms，不是网络RTT。真实测试支持累积问题已解决，但固定缓冲仍有优化空间，也不能证明长期弱网稳定性。
