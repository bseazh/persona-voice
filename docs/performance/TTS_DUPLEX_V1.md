# 当前千问 TTS：duplex-v1 实验

## 修改

- 一个回复对应一个 LiveKit SynthesizeStream 和千问合成会话。模型文本片段到达即发送，不等待整句完成后才建连。
- 文本发送和 PCM 接收并行，达到至少8字符的自然标点边界时发送供应商 flush；flush 不结束输入。
- 最后停止输入并继续接收尾部音频；插话取消时关闭连接、清理接收任务；开连接期间取消也等待启动任务收束后关闭。
- 使用官方 SDK 的 send_text/flush/stop/audio_chunks，未修改 LiveKit 核心。保留 QWEN_TTS_MODE=sentence 回退，默认 duplex-v1。
- ASR 轮次配置保持恢复后的 baseline（VAD0.5s、最小等待0.45s）；千问模型、音色、24kHz采样率不变；未启用提前生成。

## 已执行验证

2026-11-05 两项适配器测试通过：剩余文字未结束前收到音频、同一回复不按句重连；取消时释放待接收连接。两项结束语流程测试通过。

服务器真实千问测试返回：首音频0.597秒，非静音音频6.66秒，峰值19535。第二段文字在第一段音频到达之后才发送。这是独立供应商测试，不是手机端到端延迟，也不是ASR/LLM电话测试。

## 计时边界

旧按句模式先切句再创建供应商请求；新模式更早发送文本，部分文本缓冲可能计入TTS首音频。不能只看“切句变小”就判定收益。除服务端总响应外，重点比较 llm_node_ttfs + tts_node_ttfb（模型开始至首音频路径），并保留原始SDK字段、当前TTS供应商/模型/音色/模式。

## 电话测试计划与限制

本轮测两通，逐轮记录总等待、ASR收尾、模型首字、首段时间、当前千问TTS首音频、打断、结束原因。每通结束追加Issue #3。不承诺网络、供应商负载和手机听音延迟已经分离测量；不把不同问题导致的差异当因果结论。TTS自然度、句间衔接和打断残留需接听方反馈。
