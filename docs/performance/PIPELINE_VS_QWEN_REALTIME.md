# 路线对比：ASR + DeepSeek + TTS 与 Qwen 原生实时语音

更新：2026-11-05。此文汇总已有测试，不代表本轮新增拨号或更改生产参数。

## 结论

建议把 **Qwen 原生实时语音作为低时延交互的优先试验路线**，保留原流水线作为可配置、可替换模型的路线。现在不能宣布全面替换或给出“提速百分比”：两条路线的测量起点不同，实时路线只有一通真实电话，且该通自动挂断失败，修复后尚未重新完成真实电话验收。

旧流水线已测各阶段的单通平均等待为 **2.378～3.601 秒**；最新停说后提前生成版本两通为 **3.601 / 2.820 秒**。Qwen 实时路线记录的平均 **0.904 秒** 是“收到供应商停说事件后 → Agent 输出”，缺少事件之前的等待。两者都不是手机听筒端到端实测。

“TTS 双向流式”与“原生实时语音”不是同一件事。旧链路也已流式传输：流式 ASR → DeepSeek 流式文字 → 千问流式 TTS；它仍需协调识别收尾、模型启动和合成。新链路把普通对话的音频输入、生成与音频输出交给同一个实时模型，减少应用层串接，但仍有停顿判断、网络与播放延迟。全双工意味着输入输出可重叠，不意味着没有轮次检测或零延迟。

## 1. 两条路线能力对照

|项目|原流水线 `pipeline`|原生实时 `qwen-realtime`|
|---|---|---|
|普通问答路径|千问 ASR → DeepSeek → 千问 TTS|Qwen-Audio 实时音频输入/输出|
|语音模型（ASR 为代码默认，可由环境变量覆盖）|qwen-audio-3.1-asr-flash-streaming、qwen-audio-3.1-tts-flash|qwen-audio-3.1-realtime-flash|
|当前音色|longanhuan_v3.1|longanqian；与旧路线不同，也是听感混杂因素|
|打断|LiveKit/VAD 与应用控制协调取消|实时事件 + response/item 路由隔离旧输出|
|替换 TTS/ASR|可以单独更换，需重新测时延与取消兼容性|普通回复的声音与生成由实时模型提供；外接 TTS 将改变此路线，不能继续套用当前数据|
|业务控制与可观测性|文字阶段明确，便于独立检索、模型替换和分段计时|需验证业务模板遵循、转录完整性、工具控制；不能拆出模型内部 ASR/LLM/TTS 耗时|
|报告归档|现有转录与报告链路|复用归档；普通实时问答不使用 DeepSeek，报告仍可使用 DeepSeek|
|当前定位|保留、可回退|已上线可选试用，尚不是已完成实机稳定性验收的默认替代|

架构不代表模型必然更准确或成本更低；当前没有同题正确率与费用对照，不作结论。

### 计时口径：不能直接计算“快了多少百分比”

|指标|起点|终点|缺失 / 限制|
|---|---|---|---|
|旧链路 SDK e2e_latency|SDK 记录的用户 stopped_speaking_at|SDK started_speaking_at|包含可见识别收尾；不是手机端停说时间，也未测听筒播放|
|实时路线本次 0.904s|服务器收到 Qwen speech_stopped 事件|SDK started_speaking_at|不包含事件之前的端点检测及相关输入等待；未测听筒播放|
|目标体验指标，待补|接听端用户最后有声样本|接听端首次听到有效回复|需要共同时间基准或端侧录音标记；不能拿公网事件简单相减代替|

实时模型配置的静音阈值为 500ms，**不能机械地把 0.904 + 0.500 当成实测手机响应**。新路线按时间邻近关系配对停说与生成事件，还不是全程统一 trace ID。小样本不汇报稳定 P95，也不拿两种起点计算百分比或倍率。

目前没有证据把所有等待归因于 SIM、腾讯云或 TTS。旧路线的 TTS 不是零成本，但仅换 TTS 无法消除 ASR FINAL 等待。新路线也不能通过调一个独立 TTS 参数保证降低内部生成时延。

### 3.1 为什么已经流式，仍然会有两三秒延迟？

**主要问题是“数据在流动”和“系统获准开始回答”是两回事。** ASR 一边听一边给中间文字，但中间文字可能改写；正常回答仍需判定用户讲完，并拿到可用的最终文字。此后 DeepSeek 才能生成可靠回答，TTS 才能把足够的文字变成首段声音。流式减少的是等待整段输入/输出完成的时间，并没有消除每阶段首个结果的等待。

旧链路可理解为：`用户声音 → 本地停说检测 / 供应商识别并行 → 正式轮次确认 → LLM 首字 → 首段可合成文字 → TTS 首音频 → LiveKit/SIP/手机播放`。提前生成能让其中部分阶段重叠，所以这不是永远串行相加的公式。

|等待来源|代码与实测依据|目前能确认的原因|尚不能确认的内部原因|
|---|---|---|---|
|ASR 最终结果|`qwen_streaming_stt.py` 持续收发音频；只有供应商 `result.is_sentence_end()` 才发 FINAL，其他文字是 INTERIM。v1 第二通真实 FINAL 晚于 SDK 停说 1.157～2.489s|有中间文字不代表正式结果已经就绪；供应商句末结果到达是一个实际等待门槛|该时间内供应商端点检测、推理/排队、上行/下行网络各占多少，未拆分；不能称为全部“ASR 计算慢”|
|本地轮次收尾|`agent.py` 使用 Silero VAD 与 endpointing；`turn_profile.py` 控制静音与最小等待。降到 0.35/0.30s 后，最终转录与收尾仍几乎同时完成|本地检测更快，但较迟的 FINAL 仍限制正式轮次，缩短本地等待不能保证更早回复|不是把 VAD 0.5s、endpoint 0.45s、FINAL 延迟全部相加；它们存在重叠，具体轮次以日志为准|
|DeepSeek 首字|`agent.py` 将识别文本交给独立 DeepSeek 服务；本地收尾实验第一通首字均值 0.710s|ASR 后又有一次模型请求与首输出等待；流式生成不用等完整回答，但仍要等第一段输出|请求传输、服务排队、上下文处理、生成计算尚未独立计时|
|文字切段 / 缓冲|旧按句模式先积累可合成句子；第一通实验首字后切句均值 0.277s。新 `QwenDuplex` 收到文字就 send_text，在累计至少 8 字且当前片段带标点时主动 flush|等待足够文字和自然边界有利于可理解发音，但会推迟首段可播放声音；已改为边送边收，未等待完整 LLM 回答|服务商是否在 flush 前自动输出以及内部最小缓冲策略，不能从这段代码断言；不能把全部 TTS 首包时间归因于 8 字条件|
|TTS 建连与首音频|`qwen_tts.py` 在收到首个文本片段时调用 connect/start，再 send_text；每个回复仍建立合成会话，输出接收与文字发送并行。第一通实验 TTS 首音频均值 0.570s|按句反复建连已减少，但每次回复的会话启动、传输、合成首包与缓冲仍存在|没有单独的 start 完成/首文本发送/flush/供应商首音频时间戳，无法说握手占多少；跨回复复用是否支持取消隔离需先验证官方 SDK|
|提前生成失效|`preflight.py` 发候选、不冒充 FINAL；v1 两通 20 次提示，生成记录取消 7/10 次。最终识别可能改字或补全|候选早于完整问题生成，后续文字变化时需撤销或重新生成；提前请求不等于最终播放更早|取消统计不是候选命中率，也不是全部浪费的 token；不能把所有取消归咎预生成|
|播放和电话链路|上述计时终点仅为 Agent 输出，之后还有 LiveKit、SIP/RTP、网关与手机播放|这些是用户听感中的后续阶段，当前统计没有覆盖|尚未测各段缓冲、抖动或丢包，不能直接断言“线路造成了一秒延迟”|

另一个容易误读的配置是 `transcription_timeout=4.0`：这是等待转录的超时上限，不是每轮固定 sleep 4 秒；现有 2～3 秒样本也不支持固定等 4 秒的解释。当前 ASR 的 flush 不会主动关闭长期会话，不能通过每次停顿强制断开来假装立即获得 FINAL。

### 3.2 当前归因结论及如何继续证实

**已定位到的主要等待段是识别收尾，随后是 LLM 首输出和 TTS 首音频；没有定位到单一代码缺陷能解释所有延迟。** 以本地收尾实验第一通为例，3.032s 中收尾约 48.4%、LLM 首字约 23.4%、切句约 9.1%、TTS 首音频约 18.8%，余下为调度。比例只适用于该通；提前生成存在重叠的轮次不套用这些占比。

这解释了历史优化的效果：缩短本地静音没有搬走 FINAL 门槛；双向流式 TTS 减少了切句建连，却没有消除 ASR 和 LLM 等待；提前生成试图把两段等待重叠，但候选不稳定、反复作废，尚无稳定收益。

要再向下追溯，下一轮应补以下观测，而不是先猜测供应商故障：

- ASR：同一音频帧时间轴上的最后有声位置、本地 VAD 通知、完整中间文字首次出现、真实 FINAL 收到时间；用每轮 ID 关联，区分识别内容早就完整但句末很晚与内容本身一直未完整。
- LLM：请求提交、首 token、首段可合成文字、取消与采用结果；区分请求晚启动和模型本身首输出慢。
- TTS：connect/start 开始与完成、首文本发送、首次 flush、首 PCM 收到、首次送入 LiveKit；用同一段文本做至少两次受控实验，不能只看不同问题的均值。
- 电话：Agent 输出到接听端实际播放的独立测量；没有这项之前，线路只列为未测因素。

原生实时语音的潜在优势在于：普通回答不需要应用依次等待独立 ASR FINAL、DeepSeek 和独立 TTS，再串接三套输出；但模型内部仍存在识别、理解和生成等待，不能称为“消除了 ASR/TTS”。目前 0.904s 只量到其停说事件之后的部分，内部阶段尚不可拆开。是否值得默认替换，仍需第 4 节的同口径测试证明。

以上代码依据可固定查看 [f011400 版本 services/agent](https://github.com/bseazh/persona-voice/tree/f011400/services/agent)，不把后续代码变化混入本次原因判断。

## 4. 下一轮调整顺序（建议，尚未执行）

1. **先做统一测量并补挂断验收。** 两条路线使用同一位置的音频观测起点与同一首音频终点，另保留供应商事件明细；记录每轮 ID、取消、实际播放和结束原因。相同线路、相同问题集，A/B 各两通，每通至少五个完整问答，交错测试降低时段偏差。真实手机自动挂断单独验收，不能被低平均时延掩盖。
2. **优先在实时路线测试简短发言。** 首轮只改提示策略：直接回答、一般一两句、每次最多一个追问，复杂问题按用户需要展开。统计首音频、单次发言长度、打断后残留、答案覆盖与人工听感。减少播放时长不直接记为首响应提速。
3. **再做轮次检测实验。** 先保留 500ms；有统一基线后才单独测试更短阈值。实时首通出现六个 response 取消、两个已播放回答被打断；取消不全是错误，但说明不能只追求更早抢答。长句停顿、继续补充、噪声需一起验收。
4. **模型或线路优化靠分段证据。** 若新路线同口径仍主要等待模型首音频，再测模型/地域选择及连接稳定性；若 Agent 输出后仍长时间听不到，再查 RTP 抖动、网关缓冲与手机端播放。供应商支持、权限及配置需实际确认，不能猜参数。
5. **保留流水线路线。** 若业务需要指定 DeepSeek、独立音色供应商、严格文字审查或知识库控制，则独立评估流水线低延迟 ASR；不把更换 ASR、TTS、提示词和 VAD 放进同一轮实验。实时路线业务能力未验收前不删除原链路。

建议决策门槛：同口径两通以上、正确回答与完整转录、可打断、一次结束语后真实手机释放均通过，才讨论默认切换；更长期稳定性与成本另外验收。本次仅提交对比讨论，不变更默认路线、不拨号。
