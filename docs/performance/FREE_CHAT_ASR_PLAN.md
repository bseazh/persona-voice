# 自由对话测试与识别收尾排查

## 本轮变更

用户要求取消健康调查。新会话模板改为 free-chat-v1：由用户自由提问，AI 直接回答，不执行固定问卷或收集健康字段；开场、网页模板、摘要与导出名称同步调整。保留转录、打断、结束语播放后归档。历史 sleep-v1 会话与已有计时保留。

这次只改变对话内容和计时供应商标签，不调整 VAD、ASR 结束参数、LLM 提前生成或 TTS 流式实现。旧基线会话 c98783d7-7f0c-4cf5-a88f-5550a597f50a、65203bf6-78c9-43f3-9c33-943ec51fe21e 属于睡眠模板，不能把自由对话的不同问题带来的速度差异当成优化收益。自由对话需重新记录两通对照，保留至少几句相同测试问句用于比较。

## 识别收尾指什么

说话音频已持续发给 ASR；“收尾”是从用户停止说话到 Agent 确认这一轮结束、可以开始回复的等待。它涉及本地 VAD 停顿判定、供应商最终转录到达、框架轮次结束判定。这些过程会重叠，不能直接相加。

当前配置：VAD 静音 0.5 秒；endpointing min_delay 0.45 秒、max_delay 1.5 秒；transcription_timeout 4 秒；咨询模式提前生成关闭。4 秒是等待上限，不代表每轮固定等4秒；0.5与0.45也不能不看框架实现就当成固定0.95秒。

上一通7轮足量样本：收尾均值1.409秒、占总等待48.9%；其中多个轮次最终转录延迟与收尾几乎一致。另有一轮最终转录0.091秒、收尾0.451秒，说明有时是本地轮次判定在等待。不同轮次的瓶颈不完全相同。

## 下一轮优化顺序

1. 自由对话基线两通，每通至少5轮，包含短句、长句、句中停顿和插话。记录最终转录、收尾、模型首字、首段、TTS首音频和总等待；人工标记误切句、抢话与漏字。
2. 按轮判断：最终转录晚则先查千问流式ASR的句末判定及最终结果到达；最终转录早、收尾仍长则检查本地VAD/endpointing。需要更细区分时增加同一时钟的采集事件，所有对照使用相同测量开销。
3. 核实当前模型/API支持的句末参数后，才改变一个参数做两通测试。SDK存在parameters透传不等于服务端支持任意参数，不能猜参数名。若服务端不支持可调句末，则转向可验证的本地等待调整，或在后续独立阶段试验提前生成。
4. 调整静音/轮次等待时小步进行，测速度同时测句中停顿误判。发现抢话、漏识别或回答错半句则回滚，不以降低等待为唯一标准。两通结果都追加Issue #2。

本轮没有提前修改这些参数，没有宣称已获得加速。

## TTS 如何计时与替换

仍纳入服务端总等待，分项命名为“当前千问 TTS 首音频”，不把语音内容全部播放完的时间混入首响应。每个新会话记录供应商、模型、音色、采样率和输入输出模式。当前为 DashScope/Qwen、qwen-audio-3.1-tts-flash（默认值，配置可覆盖）、24kHz、按句输入/PCM分块输出。

上一通足量样本的千问 TTS 首音频均值0.510秒、占17.7%，优先级低于收尾但并非可以忽略。以后更换音色或供应商应建立新的TTS对照组；保持ASR、LLM、文本片段和网络尽量一致。TTS首音频、发言时长和人工自然度分开比较。跨供应商必须保持同一计时边界，不能拿一个供应商首字节和另一个完整合成时长相比。

本轮不拨号。待自由对话配置部署后，再进行新的基线测试。
