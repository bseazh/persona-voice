# 04 提前生成：能否把模型等待与收尾重叠？

## 当前结论

GitHub Issue：[本阶段测试与优化历史 #4](https://github.com/bseazh/persona-voice/issues/4)。

已部署并实测 preflight-v1（cd67eec）。两次真实电话均完成，但没有稳定降低时延，第一通接听方明确反馈“不自然”。默认回退为 VOICE_PREFLIGHT=off，保留显式开启供后续实验；不把本轮标记为优化成功。

## 优化前

参考上一阶段：[第1通](tts-duplex-v1-1.md) 5轮非中断回复，均值2.910秒；[第2通](tts-duplex-v1-2.md) 3轮，均值2.537秒。自由话题、小样本，不能作为严格控制实验或声称因果收益。

## 计划变更与原因

中间识别至少6字符、稳定300ms后提供候选；每ASR句最多2个不同候选，SDK每用户轮最多2次尝试、说话超过10秒停止提前生成。保持 baseline 停顿参数与 duplex-v1 TTS；关闭提前TTS。

LiveKit 1.8.10 在采用候选前校验最终文字、上下文、工具配置；文字变化时取消旧候选。工具执行受正式轮次授权约束。不会将 interim 伪造为 FINAL。

新增稳定提示取消、去重、预算、关闭与异常隔离5项测试；现有TTS并发2项、结束播放2项回归测试通过。SDK授权门源码已检查；真实通话中抢话、打断与结束行为仍须验收。

观测 asr_preflight / asr_final 时间、生成取消状态与原有轮次计时。生成记录不代表实际播放；SDK transcription_delay 受预识别时钟影响，不作为真实FINAL等待的独立依据。并行阶段不强制计算100%占比；不宣称已经测得手机端听音时延。

回滚：服务端设置 VOICE_PREFLIGHT=off，在无通话时重启 Agent。额外候选可能增加 LLM token 费用，先以两通测试评估，不扩大自动呼叫数量。

## 本轮解答与决策

两通对应上一阶段2.910 / 2.537秒，本轮2.378 / 2.855秒，方向不一致。ASR真实FINAL核对显示第二通仍等待1.157～2.489秒；不能用提前提示的SDK时钟伪装为识别加速。没有手机端音频采样，网络贡献尚不能定量。

候选生成时机过早：两通共有20次提示、35次模型生成记录、17次生成取消，19个完成的speech handle未进入播放调度。第一通某轮最后候选10字符、最终45字符；第二通某轮候选18字符、最终51字符。300ms稳定窗口不能充分代表说完话，重试预算可能在完整句子到达前耗尽。不能从这些计数推算真实token账单或精确采用率。

决策：默认关闭本轮提前生成，保留TTS双工和baseline停顿参数。后续优先设计“检测到停说之后，用最新稳定中间结果准备一次候选”，并测量候选与FINAL的一致性；不增加请求次数来掩盖问题、不伪造FINAL、不宣称线路是主要原因。下一版仍须独立两通验收。

两通均无voice.error且完成farewell_played，但第二通用户发现结束语重复。日志确认普通流式回复先播出感谢语，finish_consultation随后再次say近似同句。这是业务结束流程重复，不是音频回声。修复说明见 [结束语重复排查](FAREWELL_DUPLICATION.md)。该修复发生在两通之后，不能用本轮电话作为修复验收。
