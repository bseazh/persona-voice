# Qwen 全双工：真实电话第 1 通及告别未挂断故障

日期：2026-11-05。Issue #6。会话 `0e41ed43-01ec-42ec-9d32-7190aa50e83c`。

生产实现 `1243803`；拨号时仓库 HEAD `9b2f182`（后者只增加报告与探针）。路线由 `voice.benchmark_config` 确认为 `qwen-realtime` / `qwen-audio-3.1-realtime-flash`，server VAD 静音 500ms。本次只拨打 1 通；没有自动补打。

## 结果

实际接通，保存 24 条双方文字；7 个完整非中断回答计时（包括最后的口头告别），另 2 个已播放但被打断的回答；开场不计入响应统计。完整回答平均 0.904 秒，中位数 0.917 秒，最小 0.491、最大 1.214 秒。

**这不是用户真正停说到手机听到的时延。** 起点是服务器收到 Qwen 的 `speech_stopped`，终点是 SDK 的 `started_speaking_at`（Agent 输出）。前面的静音判定、输入网络，以及后面的 SIP/蜂窝/听筒延迟没有计入；不能把 500ms 参数直接当作精确实测补上，也不能与旧流水线不同起点的数字直接计算提速百分比。

配对方式：按同一服务器时钟寻找播放开始前最近的 response.created 及其最近的 speech_stopped；要求两者间隔不超过 1 秒，且 speech_stopped 至播放开始之间没有新的 speech_started。模型指标通过 request_id 关联 response_id。本通 9 个已播放回答均满足这些时间约束；没有声称这是跨系统端到端的严格 trace ID。

## 自动挂断：失败，用户已确认

最后用户表达的是带重复应答词与口语单字“拜”的告别，模型回复“好的，再见。”；原结束规则未识别该完整转录，模型说再见并没有进入结束状态机。

- `voice.ending`、`voice.farewell_played`、`voice.phone_release` 均没有记录。
- 06:44:59.057 UTC 记录 `participant_disconnected`；06:45:00.808 UTC 记录 `channel_closed`。两者不能证明 AI 主动挂断。
- 接通至服务端通道关闭约 163.672 秒。直接触发下游断开的主体未独立确认。
- 用户明确反馈最后一句“好的再见”后没有自动关闭，本项验收失败。
- 没有 `voice.error`，但“没有 API 错误”不等于业务闭环成功。

修正方向：补充“那就这样 + 拜/拜拜/再见”的完整口语结束形式；保留对否定、引用、假设表达的保护，不以助手说“再见”直接强制挂断，也不把含糊的“那就这样吧”无条件当结束命令。新增实际转录回归和重复结束幂等测试；随后使用同一最终转录回放到真实模型控制器，单独记录修正验收。

## 流畅度的下一步

1. 优先修复本次结束闭环；不改时延参数，避免把修复与性能实验混在一起。
2. 4 个完整回答的播放时长达到 10～14 秒。下一轮可检验更短的首句和更少连续解释，改善轮流说话的节奏；当前只是有数据支持的优化候选，未声称实施。
3. 本通有 6 个 provider response 被取消，其中 2 个回答实际开始播放后被打断。多次停顿后继续说触发切段，不能盲目把 500ms 静音再调低。
4. 手机听筒端时间尚缺。要判断网络/网关贡献，应使用双方授权的统一时间标记或端侧观测，不能把服务端小数当作手机实测。
