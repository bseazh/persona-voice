# 结束语重复：定位与修复

## 真实证据

会话 73ca29d6-65e9-40f1-a58e-dde289547873，preflight-v1 第2通。
模型普通回复先播放“好的，那今天就到这里，谢谢你和我聊这些。”，结束工具随后以 say 再次播放“好的，那今天就到这里，谢谢你和我聊这些，再见。”。
两个不同的 assistant 消息、generate_reply 与 say 两个播放来源，说明是程序重复播报，不是SIM线路回声。

## 根因

原结束工具等待普通回复播放完毕后，无条件调用 session.say(farewell)。LLM允许在工具调用前产生自然语言，所以同一结束语走了两条播放路径。原有 finishing 检查也没有在控制器入口做幂等保护。

## 修复

- 提示模型结束时仅调用工具，结束语只放在 farewell 参数中，不同时输出普通回复。
- 等待当前工具所在轮次的普通语音播放完成，检查该 speech_handle 的最后一条完整助手消息。若它与工具结束语为同一前缀（忽略标点，至少6字符、覆盖工具文本70%以上），复用已播结束语，不再次合成；不查旧轮次，也不复用被打断或无关的文字。
- 如没有已播匹配项，仍正常合成结束语、等待播放后再归档挂断。
- 控制器 finish 入口幂等保护，重复结束请求只处理一次。新增 farewell_reused 审计事件。

## 验证与限制

新增回归用例复现普通回复＋工具参数相差“再见”的情况：播放未完成时不挂断，播放完成后不再调用TTS；重复finish不二次归档。短应答、无关文字和被打断内容不被误判为已播结束语。现有正常结束、播放失败测试继续通过。

本轮两通电话已完成，未为此额外拨第三通。修复后仍需下一次真人通话验收。当前匹配是保守的近重复检查；语义相似但措辞完全不同的结束语依赖提示约束，不能承诺已覆盖所有改写。
