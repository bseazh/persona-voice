## 当前实际结果

2026-11-05 旧线路尝试两次，均 `phone_not_connected`，各有 0 个有效轮次。拨号等待约 34.37 秒，仅表示未接通等待，不能当作 AI 响应延迟。没有测得 ASR、LLM、TTS 分段耗时及占比。

用户随后调整主被叫并更换 SIM，软件仍使用 SIM 2（逻辑槽位 1）；手机系统显示中国移动卡，完整号码被系统隐藏。新线路必须重新完成两通基线，实际主叫以接听手机来电显示为准。完整号码与私人转录不写入本档案。

## 每轮必须回答的问题

1. 优化前卡在哪里？给出两通有效测试的会话 ID、逐轮时间和异常。
2. 本轮具体改了什么？为什么？保留参数与代码版本。
3. 优化后两次分别怎样？给出分段时间、占比、总等待、打断及听感。
4. 比前一阶段改善还是退步？不能量化时标记“待测”，说明原因；决定保留或回滚。

基线两通；每项优化增加两通，前值引用紧邻上一阶段的两通，共至少 10 通有效电话。失败尝试单列且不覆盖。每通至少 5 轮，固定模板与网络环境，包含停顿、插话、结束语。

## 如何维护

工作簿黄色区域用于填入真实数据，“99 示例非实测”只展示格式和占比公式，绝不混入统计。填写时必须附会话 ID；每阶段更新独立 Markdown 的解释与决策，完成重算并检查公式后提交 Git。工作簿按两通等权平均比较，不把平均的中位数当总体中位数。

`scripts/build-latency-workbook.py` 用于初次生成模板，会覆盖工作簿与阶段说明；已有人工填写后不要直接重建。`scripts/benchmark-phone.cjs` 保存私人原始事件，`scripts/report-phone-latency.py` 生成本地逐轮报告；提交前只提取白名单计时字段到本目录，禁止提交 API Key、管理员密码或完整健康转录。

当前没有实施四项优化，也没有宣称优化收益。已部署的只是 SDK 计时日志；两个语音结束流程测试通过。
