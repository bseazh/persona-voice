# 03 TTS流式：首句与句间播放为何等待？

## 当前结论

GitHub Issue：[本阶段测试与优化历史 #3](https://github.com/bseazh/persona-voice/issues/3)。

已实现并部署 duplex-v1（代码3f68822）：同一回复持续发送文本、并行接收PCM。服务器真实测试确认音频在后续文字发送前已返回。两通真实电话完成，均farewell_played、未记录voice.error。保留实现与QWEN_TTS_MODE=sentence回退，不宣称已达到自然低延迟目标。

## 优化前

上一阶段自由对话两通完整回复均值3.032秒（7轮）、3.347秒（4轮），但使用local-fast-v1；本轮恢复baseline ASR参数后改变TTS。没有同题、同网络条件的严格A/B对照，数值差异不等于TTS因果收益。模型、音色和采样率保持一致。

## 计划变更与原因

在一个回复内持续提交文字并接收音频，检查连接复用与取消清理。

实现及独立测试见 [duplex-v1方案](TTS_DUPLEX_V1.md)。一个回复一个合成会话；自然标点边界flush不结束输入。插话关闭连接，结束语等待尾部音频播放；两项适配器测试与两项结束流程测试通过。

## 本轮解答与决策

两通相对上一阶段对应均值数值减少约0.122秒、0.810秒，但因话题、ASR参数、供应商波动等差异，不将其作为改善率承诺。两通完整回复的“模型开始至首音频”合计均值分别约1.375秒和1.359秒；保留该合计指标避免流式切句计时边界迁移产生误读。

ASR最终转录仍通常等待1秒以上，不能归因于“全部都是线路问题”，也无法用当前日志分离供应商计算与公网网络。第二通样本偏少；打断日志不代表手机端立即无残音，人工听感待反馈。

决策：保留duplex-v1，继续保留供应商和音色标签；无需换千问Key。ASR仍为baseline，提前生成关闭。后续若继续优化，优先明确ASR最终结果等待与可用的提前生成边界，不能把中间转录伪造成最终结果。若出现断句、吞字或残留音频，切回sentence并留存失败原因。
